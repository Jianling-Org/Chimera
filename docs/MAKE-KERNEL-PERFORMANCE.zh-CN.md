# make 编译内核：早期8核与16核对照

本文保留2026-10-15至22日的构建对照与故障定位。早期原生组使用 `-j8`，自动组使用 `-j16`；后续[同16并发实验](../experiments/gcc-performance/k3-20261030/README.md)三组均为 `-j16`，使用新轮次，不混合下列时间。

## 对照条件

| 组别 | CPU | make 并行度 | 迁移策略 |
|---|---|---|---|
| X100 基线 | 0–7 | `-j8` | 不加载 bootstrap，不启用迁移 |
| 异构实验 | 0–15 | `-j16` | 注册的编译工具链经 bootstrap 初始化后迁移 |

两组使用同一重编 make、GCC、内核源码和配置，关闭 ccache，固定 KBUILD 时间、用户、主机及版本信息。模块构建不在默认计时范围；配置生成和准备过程不计入完整编译时间。

编译链包含 make、shell、xgcc、cc1、汇编器、链接器及辅助程序。未注册程序保持未就绪；仅观察到并行任务分布不等于编译器发生迁移。每轮须核对实际 CPU、COMMIT ACK、产物 SHA、退出码、账本及内核状态，不能把 `-j16` 当作16核使用证明。

## 工具链与运行问题

早期系统 GCC 基线耗时1123.5600秒，产物 Image SHA 为 `ed9e7c27ec40e4455140404a2c39507d79932992c22c80aece01fb80aacca76e`。该系统二进制的检查报告仍有3581项发现，不能登记为可迁移编译器，也不能用于后来重编 GCC 的加速比基线。

regex 堆分配候选完成 xgcc/cc1 严格检查与 Workspace 准备后，小规模16对象预检全部产物和运行输出一致，采样到4个 cc1跨组运行，迁移计数增加 X→A 7次、A→X 2次，退出账本归零。

完整构建仍暴露两类问题：

- GCC 子进程等待被策略信号以 `EINTR` 打断，随后增加 `SA_RESTART`。
- make 在 jobserver 的等待路径遇到嵌套信号帧的 `bad frame`，详见[故障记录](BOOTSTRAP-NESTED-SIGNAL-FAILURE.zh-CN.md)。`sixteen-v2` 失败于486.17秒，退出2，不计入性能样本。

静态分组诊断的[标量启动器](../experiments/make-kernel/group-shell.c)在 exec 新 shell 前确定分组，之后编译任务不跨组。64目标预检覆盖 CPU0–15，全部对象 SHA 一致，迁移计数不增；这是静态分组证据，不是自动迁移性能结果。

## 已记录结果

2026-10-22的 regular-first-v1全局策略版本完成两对相反顺序的构建：

| 组别 | 两次耗时（秒） | 均值（秒） |
|---|---:|---:|
| 普通 X1008 | 1050.822 / 1051.637 | 1051.229 |
| auto16 | 821.648 / 815.830 | 818.739 |

当时吞吐提升28.396%，耗时缩短22.116%。两对产物与门禁一致；GCC/make 十轮及两小时混合检查共170轮通过。该结果属于旧全局策略与不同并发协议，不用于证明后来的双策略接口，也不与2026-10-30的统计混池。[首对结果](GCC-MAKE-FIRST-COMPARISON.zh-CN.md)保留另一早期候选的输入和数值。

## 数据解释

相同工作量的速度比为 `T_native / T_auto`，耗时减少为 `1 - T_auto / T_native`，吞吐增加为速度比减一。X100和A100不同构，不能把相对核数效率解释为同构扩展效率；也不能把增加的累计 CPU 时间全部归因于某一种开销。

每轮使用新输出目录，记录时窗、CPU、温度、频率、资源、真实迁移与健康状态。Image、vmlinux、System.map、config逐项核对后再解释性能。历史输出与失败树分别保留，不以退出码0代替正确性和迁移证据。现行任务策略用法见[按进程选择迁移策略](MIGRATION-PREFERENCE.zh-CN.md)。
